# dev-doc-writer

把已确认的 Issue（需求文档）转成经人类确认的状态流转流程图、公有接口契约与可落地的开发文档。

## 适用场景

- 适用：开发文档阶段（B、C 阶段）——输入为已确认的 Issue 本地留档，依次产出状态流转流程图、公有接口契约与开发文档；用户提到「开发文档」「流程图」「公有接口契约」「设计业务模型」「明确函数公开属性」等说法时使用。
- 不适用：需求尚未收敛或未确认（由 `issue-writer` 处理）；任务拆分、编码实现、测试计划与执行、PR 提交等其他阶段（由对应 Skill 处理）。

## 必要前提

1. **输入必须是已确认的 Issue**：`docs/dev-docs/<开发序号>/` 下存在本次开发的 Issue 本地留档（`<仓库名>-<issue编号>-issue.md`）且已经人类确认。不存在或未确认时，回到 `issue-writer` 阶段，不自行脑补需求。
2. **开发序号与标题可确定**：`<开发序号>` 由 Issue 所在目录确定，`<标题>` 取 Issue 标题。任一无法确定时，先向人类确认。

## 执行约束

- 必须：只设计需求真正需要的实体、状态、事件、接口与函数，不添加需求之外的内容（奥卡姆剃刀）。
- 必须：以「能正确完成需求」为第一设计目标，不以技术偏好或代码风格为先（需求优先）。
- 必须：流程图、公有接口契约与开发文档的终稿都交由人类确认；人类已给出设计时，先判断其能否满足需求——能满足则优先采用，不能满足则说明理由并给出可行方案（设计终稿由人决定）。
- 必须：按「状态流转流程图 → 公有接口契约 → 开发文档」的顺序执行，上一环节未定稿禁止进入下一环节；下游禁止出现上游未定义的状态、实体或接口（顺序不可跳过）。
- 必须：开发文档中的状态枚举、实体、接口、错误码与流程图、公有接口契约保持一致；发现不一致时回到对应上游环节修订，不在下游补丁式兜底。
- 禁止：新增公有接口契约之外的公有接口。
- 禁止：出现未决项；未决项必须询问人类并确定为已决项。
- 禁止：在同一份文件中并存原设计与修改后设计，设计文档只记录最新设计；迁移记录只记录新设计与原设计的不同（而非原设计全部内容），放置于 `docs/dev-docs/<开发序号>/migration-info/` 下，命名为 `<序号>-<迁移内容概况>.md`（`<序号>` 为该开发序号下迁移记录的递增序号）。
- 只能修改：`docs/dev-docs/<开发序号>/` 目录；除流程图、公有接口契约、开发文档与设计迁移记录外，不新增其他文件或目录。

**参考文件**：本 Skill 附带以下参考材料，此处仅**显式声明其存在**，不展开其正文：

- `assets/flowchart-template.md`（状态流转流程图模板）：**仅在设计业务模型与状态流转流程图时**读取；
- `assets/interface-contract-template.md`（公有接口契约模板）：**仅在确定公有接口契约时**读取；
- `assets/dev-doc-template.md`（开发文档模板）与 `references/function-design-rules.md`（函数必含内容、公有接口设计规范、校验规则）：**仅在制作开发文档时**读取；
- `references/call-relationship-rules.md`（同模块 / 跨模块调用方式与依赖注入约束）：**仅在设计函数间的调用关系时**读取；
- `references/resource-lifecycle-rules.md`（数据结构所有权、销毁顺序与借用 / 共享约束）：**仅在设计数据结构与对象销毁行为时**读取；
- `references/visibility-attributes.md`（函数公开属性定义）：**仅在确定函数与公开属性时**读取。

## 工作流程

### 1. 读取 Issue，确定标题与开发序号

读取 `docs/dev-docs/<开发序号>/` 下的 Issue 本地留档（`<仓库名>-<issue编号>-issue.md`），确认本次开发要完成的需求、期望行为与期望结果。

- `<开发序号>` 取自 Issue 所在目录；目录不明确时向人类确认。
- `<标题>` 取 Issue 标题；标题不明确时向人类确认。
- 后续三份产物共用同一 `<开发序号>` 与 `<标题>`。

### 2. 设计业务模型与状态流转流程图草稿，并由人类确认

依据 Issue 设计一份能完成全部需求的业务模型与状态流转流程图草稿，至少画出：

- **核心实体**：业务对象及其关键属性、实体间关系；
- **生命周期与状态**：状态集合、每个状态的含义、是否终态、进入条件与退出条件；
- **事件**：触发状态变化的事件、触发方与触发时机；
- **流转约束**：允许 / 禁止的流转、并发与幂等要求、异常与超时分支、终态约束。

流程图须覆盖 Issue 中的全部期望行为与期望结果，不得遗漏异常分支。

- 目录：`docs/dev-docs/<开发序号>/`；
- 命名：`<标题>流程图.md`。

保存草稿后，明确告知人类草稿路径并请其查看，然后**通过提问的方式逐项确认**（优先使用 `AskUserQuestion` 给出可选方案），至少确认：

- 核心实体与关系是否齐全，是否有需求之外的多余实体；
- 状态集合与生命周期是否完整，终态是否明确；
- 每个状态的进入 / 退出条件、触发事件与触发方是否准确；
- 非法流转、并发、幂等、异常与超时约束是否符合设想；
- 流程图能否覆盖 Issue 的全部期望结果。

人类提出修改意见时，直接修改该文件并再次确认，直至人类明确认可。认可后的内容即正式流程图；文件内只保留最新设计，不得并存草稿与修改稿。

### 3. 依据正式流程图确定公有接口契约，并由人类确认

只依据已确认的正式流程图设计公有接口契约，不得新增流程图之外的状态、实体或业务规则。

草稿必须包含：

- **URL** 与**方法**；
- **入参**与**出参**，并明确每个字段的**类型**、是否必填与含义；
- **错误码**及每个错误码对应的错误场景；
- **状态枚举**：枚举值与含义，必须与正式流程图的状态逐一对应，不得增删或改名；
- **幂等规则**：幂等键 / 判定依据，以及重复请求的处理与返回。

公有接口契约设计约束：

- 每个会改变状态的接口，应在说明中写明它触发的事件与状态流转；
- 错误码须覆盖黑盒校验失败、状态不合法、资源冲突等失败场景，并与流程图中的流转约束对应；
- 查询类接口默认幂等；写类接口必须显式声明幂等规则，不得留空。

- 目录：`docs/dev-docs/<开发序号>/`；
- 命名：`<标题>公有接口契约.md`。

保存草稿后，明确告知人类草稿路径并请其查看，然后通过提问逐项确认，至少覆盖：URL 与方法、入参 / 出参字段与类型、错误码、状态枚举、幂等规则。人类提出修改意见时，直接修改并再次确认，直至人类明确认可；认可后的内容即最终稿。

### 4. 依据正式流程图与公有接口契约制作开发文档

只依据已确认的流程图与公有接口契约设计开发文档，不得引入二者之外的状态、实体、接口或业务规则。

#### 4.1 确定函数与公开属性

- **公有接口**：只有与公有接口契约相关的函数才是公有接口；每条公有接口契约对应其对外暴露的函数（一个接口有多个方法时按方法分别定义）。
- **私有函数**：公有接口契约之外的函数，公开属性一律默认为私有函数。
- **公有函数**：私有函数中，仅当存在**模块内跨文件调用**需求时，才设为公有函数。

不得新增公有接口契约之外的公有接口。

#### 4.2 确定多线程属性

依据需求明确每个函数的多线程属性（普通 / 并发 / 异步）：

- 需求涉及多线程、并发或网络请求 → 逐函数标注；
- 需求不涉及 → 不作设计，默认普通函数。

#### 4.3 制作开发文档

- 目录：`docs/dev-docs/<开发序号>/`；
- 命名：`<标题>开发文档.md`。

开发文档须与流程图、公有接口契约保持一致：状态枚举、实体、接口、错误码不得出现上游未定义的内容；发现不一致时回到对应上游环节修订，不在下游补丁式兜底。

#### 4.4 最终一致性校验

交付前确认，并提示人类查看开发文档后确认定稿：

- 流程图、公有接口契约、开发文档三者状态枚举一致；
- 每条公有接口契约都有对应的公有接口函数，且没有公有接口契约之外的公有接口；
- 每个函数都有公开属性与多线程属性；
- 无未确认项被写成已确认。

## 输入 / 输出

```text
dev_doc_writer(
  已确认Issue留档: string,           // 必填：docs/dev-docs/<开发序号>/<仓库名>-<issue编号>-issue.md，须已经人类确认
  开发序号: number,                   // 必填：Issue 所在目录的开发序号，由人类确认
  标题: string,                       // 必填：Issue 标题
  人类设计: HumanDesign | null,      // 可选：人类已给出的流程图 / 接口契约 / 开发文档设计；缺省由 AI 依据需求自行设计
) -> SkillResult

SkillResult {
  status: "success" | "partial" | "failed",
  artifacts: string[],        // 流程图 + 公有接口契约 + 开发文档路径
  errors: SkillError[]
}

SkillError {
  code: string,               // 与「失败处理」的错误码一一对应
  message: string,
  recoverable: boolean
}
```

## 失败处理

| 失败场景 | 判定条件 | 处理动作 |
| --- | --- | --- |
| Issue 留档缺失或未确认 | `docs/dev-docs/<开发序号>/` 下不存在本次开发的 Issue 文件，或该 Issue 未经人类确认 | 中断；回到 `issue-writer` 阶段，不自行脑补需求（`INPUT_INVALID`） |
| 开发序号或标题无法确定 | 无法从 Issue 所在目录确定 `<开发序号>`，或无法从 Issue 标题确定 `<标题>` | 中断；向人类询问确认后再继续（`PARAM_UNKNOWN`） |
| 流程图 / 公有接口契约未经人类确认 | 人类尚未明确认可流程图或公有接口契约终稿 | 中断；向人类逐项提问，将未决项确定为已决项后再继续（`NOT_CONFIRMED`） |
| 开发文档与上游不一致 | 开发文档出现流程图或公有接口契约未定义的状态、实体、接口或错误码 | 回退到对应上游环节修订，不在下游补丁式兜底（`INCONSISTENT`） |
| 文件写入失败 | 写入 `docs/dev-docs/<开发序号>/` 失败（路径非法、权限或磁盘错误） | 中断并保留原始报错；提示人类检查目录后重试（`WRITE_FAILED`） |

## 示例

### 示例 1：AI 自行设计并产出三份产物（成功）

输入：

```text
已确认Issue留档：docs/dev-docs/12/From-Issue-To-PR-Skill-12-issue.md（已确认）
开发序号：12
标题：订单状态流转
人类设计：null
```

关键步骤：依据 Issue 设计流程图草稿并确认 → 依据正式流程图确定公有接口契约并确认 → 制作开发文档并确认定稿。

输出：

```text
status: success
artifacts: [
  "docs/dev-docs/12/订单状态流转流程图.md",
  "docs/dev-docs/12/订单状态流转公有接口契约.md",
  "docs/dev-docs/12/订单状态流转开发文档.md"
]
errors: []
```

### 示例 2：优先采用人类设计（成功分支）

输入：

```text
已确认Issue留档：docs/dev-docs/13/From-Issue-To-PR-Skill-13-issue.md（已确认）
开发序号：13
标题：退款审批
人类设计：人类已给出流程图与接口契约（满足需求）
```

关键步骤：判断人类设计能否满足需求 → 满足则直接在其基础上确认并补齐开发文档。

输出：

```text
status: success
artifacts: [
  "docs/dev-docs/13/退款审批流程图.md",
  "docs/dev-docs/13/退款审批公有接口契约.md",
  "docs/dev-docs/13/退款审批开发文档.md"
]
errors: []
```

### 示例 3：Issue 未确认（失败）

输入：

```text
已确认Issue留档：（docs/dev-docs/14/ 下无 Issue 文件或未确认）
```

输出：

```text
status: failed
errors: [
  { code: "INPUT_INVALID", message: "Issue 留档缺失或未确认，已暂停", recoverable: true }
]
处理动作：中断；回到 issue-writer 阶段确认需求后再进入本阶段
```
