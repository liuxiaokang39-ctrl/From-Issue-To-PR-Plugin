# dev-doc-writer

把已确认的 Issue（需求文档）转成可落地的开发文档与配套流程图。

## 必要前提

1. **奥卡姆剃刀**：如无必要，勿增实体。只为需求真正需要的部分做设计，不添加需求之外的函数、数据结构、目录或章节。
2. **需求优先**：以「能正确完成需求」为第一设计目标，不以技术偏好或代码风格为先。
3. **设计终稿由人决定**：AI 先依据需求文档自行设计，但设计终稿必须交由人类决定。若人类已给出自己的设计——先判断其能否满足需求：能满足则优先采用人类设计；不能满足则向人类说明理由，并给出可行方案。

## 工作流程

### 1. 确认「目录结构.md」

`目录结构.md` 分两份，分别记录两类信息，需分别确认：

**（1）docs 的目录结构**：记录开发的迁移信息——`docs/dev-docs/` 下每个文档是什么、何时产生、对应哪一步开发，即开发过程的迁移轨迹。

**（2）本项目的目录结构**：记录本项目每个工作区的职责，即各目录分别负责什么内容。

对上述两份分别检查 `docs/dev-docs/` 下是否存在对应的 `目录结构.md`：

- **不存在** → 先依据实际结构创建：docs 的目录结构依据开发迁移信息写，本项目的目录结构依据项目实际结构逐一写清每个目录负责的内容。
- **已存在** → 读取并以其为准，不重复创建。

### 2. 明确本次设计的工作区

向人类提问，明确本次设计涉及哪几个目录，并区分：

- **读写工作区**：本次设计会新增或修改内容的目录；
- **只读工作区**：本次设计只读取、不修改的目录。

再按工作区当前状态决定设计起点：

- 工作区为**空目录** → 设计可自由发挥；
- 工作区**已有内容** → 先阅读现有相关内容，并以其为基础做设计。

### 3. 明确每个函数的公开属性

逐个函数明确其公开属性，**默认私有**。分三档：公有接口、公有函数、私有函数。

**参考定义**：本 Skill 附带 `references/visibility-attributes.md`。此处仅**显式声明其存在**；**仅在本步骤才读取该文件内容**，其余阶段不展开其正文。

### 4. 明确每个函数的多线程属性

依据需求明确每个函数的多线程属性（如并发、异步）：

- 需求涉及多线程或网络请求 → 逐函数标注；
- 需求不涉及 → 不作设计，默认普通函数。

### 5. 制作开发文档

依据上文结论与和人类的对话制作开发文档。

**参考模板与规则**：本 Skill 附带 `assets/dev-doc-template.md`（文档模板）与 `references/function-design-rules.md`（函数必含内容、公有接口设计规范、校验规则）。此处仅**显式声明其存在**；**仅在制作开发文档时才读取这些文件内容**，其余阶段不展开其正文。

**调用关系规则**：本 Skill 附带 `references/call-relationship-rules.md`（同模块 / 跨模块的方法调用方式与依赖注入约束）。此处仅**显式声明其存在**；**仅在设计函数间的调用关系时才读取该文件内容**，其余阶段不展开其正文。

- 目录：`docs/dev-docs/`
- 命名：`<序号>-<标题>开发文档.md`，序号从 `001` 开始，按项目内已有开发文档依次递增。

### 6. 制作流程图

依据生成的开发文档制作配套流程图。

**参考模板**：本 Skill 附带 `assets/flowchart-template.md`。此处仅**显式声明其存在**；**仅在制作流程图时才读取该文件内容**，其余阶段不展开其正文。

- 目录：`docs/dev-docs/`
- 命名：`<序号>-<标题>流程图.md`，序号与该流程图所依赖的开发文档一致。

## 约束

- 除上述产物与设计迁移记录外，不新增其他文件或目录。
- 未经人类确认的设计不得定稿；未决项一律显式标注为待确认，不得写成已确认。
- **禁止在同一份文件中并存原设计与修改后设计**：设计文档内容有且仅能记录最新设计。若现有设计被修改，原设计不得写入设计文档。迁移记录只记录新设计与原设计的不同，而非原设计的全部内容，并放置于 `docs/migration-info/<对应设计文档序号>/` 目录下，命名为 `<序号>-<迁移内容概况>.md`。
