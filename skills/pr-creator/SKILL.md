# pr-creator

把已验证的改动合入 `main`，通过 CI 后按 GitHub 社区规范提交 PR。

## 必要前提

1. **CI 全部通过才算提交完成**：PR 先以草稿（draft）形式创建以触发 CI；所有 CI 检查实际通过后，才可标记为可评审并请求合并。未全部通过时不得转为可评审，不得跳过、禁用、忽略检查，也不得强制合并。
2. **奥卡姆剃刀**：只修改 CI 报错明确指出的错误，不做报错之外的任何改动、重构或「顺手改进」。
3. **逻辑冲突必须暂停**：若修复必然改动代码的执行逻辑，且改动后与 `docs/dev-docs/<对应序号>-<标题>流程图.md` 的描述冲突，则立即停止提交，向人类说明冲突点与原因，等待人类决定；不得自行修改流程图迁就代码，也不得为通过 CI 而改坏流程。
4. **信息不足必须提问**：分支名、仓库类型、PR 的目标仓库无法判断时，先向人类确认，不自行假设。

## 工作流程

### 1. 明确本次需要合并的分支

向人类确认：

- 本次需要合并的分支名；
- 该分支对应的开发文档序号与 Issue 编号（用于第 5 步取 PR 标题与正文）。

无法确定时向人类询问，禁止凭提交记录猜测。

### 2. 判断远端仓库类型，fork 时先同步上游 main

用 `git remote -v`、`gh repo view --json isFork,parent` 判断当前远端是主仓库还是 fork 仓库：

- **fork 仓库** → 先同步上游：
  - 上游 remote 不存在时添加：`git remote add upstream <上游仓库地址>`；
  - `git fetch upstream`；
  - 切换到 `main`，合并 `upstream/main`（或执行 `gh repo sync`）；
  - 推送到自己的远端：`git push origin main`。
- **主仓库** → 跳过本步。
- **无法判断** → 先询问人类，不自行执行同步。

同步或推送失败、产生冲突时暂停，向人类报告，不擅自解决。

### 3. 合并待合并分支，并从 main 创建 PR

- 确认工作区干净（`git status`）；有未提交改动时先向人类确认处理方式，不强行切换或丢弃。
- 切换到 `main`，先拉取远端最新 `main`，再合并第 1 步确认的分支；
- 合并产生冲突时暂停，向人类说明冲突文件与冲突内容，由人类决定解决方式，禁止自行取舍；
- 推送合并后的 `main`；
- 以 `main` 作为 head 创建 **草稿 PR**，目标分支为上游主仓库的 `main`（fork 场景为 `upstream:main`）。

若远端即主仓库（非 fork），`main` 无法作为 head 向自身提交 PR：此时先向人类确认改用哪个分支作为 head，确认后再提交，不得自行改换。

### 4. 按 CI 反馈修复，直到全部通过

- 等待并查看 CI 结果：`gh pr checks <PR编号> --watch`；
- 失败时获取实际报错：`gh run view <run-id> --log-failed`，以报错原文为准，不猜测原因；
- 只修改报错指向的代码；修复是否改动执行逻辑，按必要前提第 3 条判断：仅当改动后的行为与对应流程图一致时才继续，否则暂停并告知人类；
- 每次修复提交并推送后，重新等待 CI，直到所有检查通过；不得只验证失败项就宣称通过；
- 全部通过后再标记可评审：`gh pr ready <PR编号>`。

### 5. 从 docs 获取 PR 标题与正文

PR 标题与正文一律取自 `docs/` 下对应序号的文件，不自行编造、不引入 docs 之外的信息：

- **标题**：取自 `docs/dev-docs/<序号>-<标题>开发文档.md` 的文件名；
- **背景**：取自 `docs/requirement-issue/<仓库名>-<issue编号>-issue.md`；
- **改动摘要**：取自开发文档中的数据结构与函数定义，并与实际 diff 对齐；
- **验证方式**：取自 `docs/test-report/<测试流程序号>/测试报告.md` 中的实际执行命令与结果；
- **影响面**：取自开发文档声明的工作区与本次 diff 涉及的文件；
- **回滚方案**：依据本次 diff 与开发文档的改动范围给出。

docs 中缺失对应信息时，向人类询问后再写，不得写成未确认的内容。

### 6. 按 GitHub 社区规范编写 PR

PR 标题、正文格式与创建命令遵循 GitHub 社区规范。

**参考文件**：本 Skill 附带 `references/GitHub-CLI.md`（gh 命令参考，含 `gh pr create`、`gh pr checks`、`gh pr ready`）与 `references/GitHub-submit.md`（Conventional Commits 规范与 Git 安全约束）。此处仅**显式声明其存在**；**仅在创建 / 编辑 PR、执行 git 或 gh 命令时才读取这些文件内容**，其余阶段不展开其正文。

用 `gh pr create --draft` 创建 PR 时按上述参考文件选定参数。使用 `--body-file` 时，临时文件放在仓库之外，PR 创建后删除，不在仓库内留下副本。

## 约束

- CI 未全部通过前不得将 PR 转为可评审、请求合并，也不得以 `--admin` 等方式强制合并。
- 不得跳过、禁用或忽略 CI 检查，不得虚构 CI 结果。
- 修复只针对 CI 报错；修复会改变执行逻辑并与流程图冲突时，必须暂停并告知人类。
- 不得自行解决合并冲突或改动合并策略；冲突交由人类决定。
- PR 标题与正文只取自 docs 对应序号文件与真实 diff / 测试记录，缺失信息先问人类。
- 除远端 PR 外不新增文件或目录；本地不保留 PR 正文副本。
