# tester

按开发文档、需求与真实实现，设计并执行三层测试：单元白盒、集成白盒、真实部署黑盒。

## 必要前提

1. **全部场景通过**：单元白盒、集成白盒、真实部署黑盒测试的所有场景必须通过。禁止虚构、推测或复用旧结果；未实际执行的场景不得标记为通过。
2. **禁止静默吞错**：执行中的报错、失败、超时与异常必须原样暴露并如实记录；不得用捕获后忽略、空断言、跳过标记或降低断言的方式掩盖失败。
3. **测试与源码隔离**：测试代码放在独立的测试目录或测试文件中，不写入生产源码；不为测试在生产源码中添加钩子、测试分支或额外导出。
4. **公开性不变**：设计与修复过程中不得修改函数 / 方法的公开属性。
5. **奥卡姆剃刀**：只为真实存在的实现写测试，不引入与真实实现无关的测试机制、mock 框架或抽象层；项目已有测试框架能满足需求时，不引入新框架。

## 工作流程

### 1. 读取输入与真实实现

读取以下内容，确定本次对应的开发文档序号：

- 开发文档：`docs/dev-docs/` 下的 `<序号>-<标题>开发文档.md`、同序号流程图、`<序号>/` 下的任务文件与 `执行顺序.md`；
- 需求：`docs/requirement-issue/` 下的 Issue 留档；
- 任务报告：`docs/task-report/`（若存在）；
- 工作区代码：逐文件读取被测目录的真实实现。

以真实实现为准校准测试预期。文档与实现不一致时，在测试文档中标注差异并按真实实现设计测试，不按文档脑补行为。

### 2. 识别公有接口

逐个函数确认公开属性：只有「公有接口」需要追加黑盒测试；公有函数做白盒断言；私有函数只声明前置条件，不重复校验。

**参考定义**：本 Skill 附带 `references/visibility-attributes.md`。此处仅**显式声明其存在**；**仅在本步骤读取该文件内容**，其余阶段不展开其正文。

### 3. 设计单元白盒与集成白盒测试

- **单元白盒**：以函数为粒度，覆盖工作区全部代码的可达路径，包含正常分支、边界值、错误返回与异常分支；
- **集成白盒**：以函数间调用链与流程图状态流转为粒度，覆盖工作区全部代码，验证模块协作、状态迁移与数据传递；
- **公有接口黑盒**：对每个公有接口，分别在单元层与集成层追加黑盒场景，只依据公开契约（入参、返回值、错误码）设计，不依赖内部实现。

两层的场景集合必须能追溯到工作区的每个文件与函数。不得以「不可达」为由默认跳过；确实无法覆盖的代码，须在测试文档中标注原因并交人类确认。

### 4. 设计真实部署黑盒测试并交人类审核

依据开发文档、需求、任务报告与真实实现，设计真实部署形态下的端到端场景：真实启动、真实依赖、真实网络 / 数据库 / 外部服务、真实用户操作路径。黑盒设计只描述外部可观察的输入与结果，不依赖内部函数。

先把「场景列表、执行步骤、期望结果、所需外部资源」告知人类，并询问是否有补充内容；经人类审核决定后，按人类结论写入测试文档。未经人类审核，真实部署黑盒测试不得定稿，也不得执行。

### 5. 生成测试流程文档

- 目录：`docs/test-process/<开发文档序号>/`；
- 文件固定为三份：`1-单元白盒测试流程.md`、`2-集成白盒测试流程.md`、`3-真实部署黑盒测试流程.md`；
- 每份文档统一按六节组织：1. 测试目标、2. 验收标准、3. 工作区范围、4. 测试步骤与期望结果、5. 测试所需外部资源（如果有）、6. 注意事项（如果有）；
- 在「工作区范围」列出被测文件 / 函数与覆盖它们的场景编号，形成覆盖清单。

**参考模板**：本 Skill 附带三份样板草稿：

- `references/unit-whitebox-test-process-template.md`
- `references/integration-whitebox-test-process-template.md`
- `references/deployment-blackbox-test-process-template.md`

此处仅**显式声明其存在**；**仅在生成对应测试文档时才读取对应模板**，其余阶段不展开其正文。

### 6. 按顺序执行测试

- 通过 shell（shell MCP / 终端）按「单元白盒 → 集成白盒 → 真实部署黑盒」的顺序执行，每份文档内按场景编号顺序执行；
- 若当前环境没有可用的 shell 执行能力，先启用或安装 shell MCP；仍不可用时提示人类安装；
- 缺少测试框架、编译器、运行时或依赖时，先自行安装；安装失败则提示人类安装，不得跳过或伪造结果；
- 每个场景记录实际执行的命令、实际输出与通过 / 失败结论；失败或异常时必须保留完整错误信息，禁止静默吞错；
- 测试代码写入项目约定的独立测试目录（如 `tests/`、`__tests__/` 等）或独立测试文件，不写入生产源码。

### 7. 处理失败

仅当失败属于以下两种情形之一时，才允许修改工作区代码：

- 代码逻辑正常，仅因入参校验缺失或未覆盖测试样例导致失败；
- 代码逻辑正常，仅因返回值格式与预期不符导致失败。

修复须保持函数公开属性不变，只做满足测试所需的最小改动。修改后重新执行受影响场景，并重新执行同文档内的关联场景与后序测试，不得只跑失败场景就宣称通过。

若失败由设计逻辑本身导致，即按开发流程图的状态流转不可能达到测试目标，则不得修改代码迁就测试。在 `docs/test-report/<测试流程序号>/` 下生成 `测试报告.md`，写明：

- 失败的测试类型与场景编号、名称；
- 实际执行的命令与结果；
- 期望结果与实际结果；
- 导致失败的设计原因，须引用开发文档或流程图中的具体函数、状态或分支；
- 为何按该设计不可能通过测试目标。

### 8. 汇报结果

向人类如实汇报每份流程文档的场景总数、通过数、失败数与未执行数，以及失败项的处理结论与报告位置。未执行数必须为 0 且全部场景实际通过后，本阶段才结束；禁止把未执行或跳过的场景计入通过。

## 约束

- 不得虚构测试结果；未实际执行的场景不得标记为通过。
- 不得静默吞错；任何错误、异常与超时必须暴露并记录。
- 不得修改函数公开属性；不得为测试在生产源码中加入钩子或测试分支。
- 不得引入与真实实现无关的测试机制；项目已有测试框架可用时不引入新框架。
- 真实部署黑盒测试未经人类审核不得定稿。
- 属于设计逻辑原因导致的失败，不得改代码迁就测试，只能产出测试报告。
- 开发文档、流程图或任务清单缺失时，回到上一阶段补齐，不自行脑补测试目标。
- 除 `docs/test-process/<序号>/` 的三份测试流程文档、`docs/test-report/<序号>/` 的测试报告，以及按项目约定放置的测试代码外，不新增其他文件或目录。
