# implementer

把已拆分好的任务清单，逐项落成代码改动，并逐任务产出任务报告、提交并推送 commit。本 Skill 位于任务拆分之后、测试与 PR 提交之前，只负责编码实现，不改动开发文档与任务清单。

## 适用场景

- 适用：任务清单已定稿，需要按 `执行顺序.md` 逐项修改代码、生成任务报告并按任务提交 commit；用户提到「编码实现」「实现任务」「按任务清单开发」「代码落地」等说法。
- 不适用：开发文档或流程图缺失（回到 `dev-doc-writer` 补齐）；任务清单与执行顺序缺失（回到 `task-planner` 补齐）；测试计划与测试执行（由 `test-planner`、`test-runner` 处理）；PR 提交（由 `pr-creator` 处理）。

## 必要前提

1. **开发文档与流程图存在**：`docs/dev-docs/<开发序号>/` 下存在 `<标题>开发文档.md` 与同目录的 `<标题>流程图.md`，且内容非空。不满足时中断，回到 `dev-doc-writer` 阶段补齐，不自行脑补设计。
2. **任务清单与执行顺序存在**：`docs/dev-docs/<开发序号>/task-list/` 下存在 `执行顺序.md` 与其中引用的任务文件 `<编号>-<任务标题>.md`。不满足时中断，回到 `task-planner` 阶段补齐。
3. **开发序号已确定**：`<开发序号>` 取自任务所属开发文档所在目录，且与 `task-list/` 目录一致。无法确定时使用 `AskUserQuestion` 向人类提问确认，不得自行编号。
4. **git 与 gh 可用**：`git status` 与 `gh auth status` 均可成功执行，当前仓库存在可用的 `main` 分支。不满足时中断并提示人类配置后重试，不得跳过提交或 push。

## 执行约束

- 必须：奥卡姆剃刀——如无必要，勿增实体。
- 必须：执行顺序取自 `执行顺序.md`，按其给出的顺序逐步推进，不自行改序。
- 必须：只改任务声明的工作区——读写工作区可新增或修改，只读工作区只读不改。
- 必须：任务达到其「验收标准」后才标记完成；每完成一项任务即生成任务报告、提交 commit 并 push。
- 必须：任务报告固定写入 `docs/dev-docs/<开发序号>/task-report/`，除代码产物与任务报告外不新增其他文件或目录。
- 禁止：在 `main` 分支上 commit 或 push；本阶段全部改动提交于从 `main` 创建的任务分支上。
- 禁止：开发文档、流程图或任务清单缺失时自行脑补，必须回到对应上游阶段补齐。
- 禁止：未达到「验收标准」的任务标记完成；任务报告缺失或未覆盖「修改的信息」「修改的文件与文件内位置」「检查结果」三项的，同样不得标记完成。
- 禁止：跳过 commit 或 push；commit 失败时禁止使用 `--amend`、`--no-verify` 绕过，必须修复后新建 commit。
- 只能修改：任务声明的读写工作区，以及 `docs/dev-docs/<开发序号>/task-report/`。

**参考文件**：本 Skill 附带下列文件，此处仅**显式声明其存在**，不展开其正文：

- `references/function-design-rules.md`（公有接口设计规范、伪代码实例、校验规则）：**仅在编写函数 / 方法时**读取；
- `references/call-relationship-rules.md`（同模块 / 跨模块的方法调用方式与依赖注入约束）：**仅在编写方法间的调用时**读取；
- `references/resource-lifecycle-rules.md`（对象销毁时独占资源的释放责任、释放顺序与借用 / 共享引用处理）：**仅在编写对象销毁、资源获取或释放相关代码时**读取；
- `references/rust-global-constraints.md`（Rust 全局约束）：**仅在编写 Rust 代码时**读取；
- `references/GitHub-CLI.md`（gh 命令参考）与 `references/GitHub-submit.md`（Conventional Commits 提交规范与 Git 安全约束）：**仅在执行 git 或 gh 命令时**读取。

## 工作流程

### 1. 了解任务全貌

读取 `docs/dev-docs/<开发序号>/` 下本次任务的开发文档与流程图，即 `<标题>开发文档.md` 与同目录的 `<标题>流程图.md`，据此了解本次任务的全貌；再读取 `task-list/` 下的 `执行顺序.md`。

开发文档或流程图缺失时，回到 `dev-doc-writer` 阶段补齐；任务清单或执行顺序缺失时，回到 `task-planner` 阶段补齐，均不自行脑补设计。三者均存在且可读时，进入第 2 步。

### 2. 创建任务分支

基于 `main` 创建本次任务的分支，本阶段全部子任务的改动都在该分支上提交。禁止在 `main` 分支上反复 commit。分支创建成功后，进入第 3 步。

### 3. 按执行顺序逐项实现

按 `执行顺序.md` 给出的顺序逐步推进，不自行改序：

- 逐个读取任务文件 `<编号>-<任务标题>.md`，按其「工作区」「验收标准」与「实现内容」完成代码编写；
- 执行每个子任务时先检查其工作区：工作区**为空** → 自行发挥；工作区**非空** → 先分析现有代码是否符合任务设计，若不符合，则依据任务设计修改现有代码；
- 只改任务声明的工作区：**读写工作区**可新增或修改，**只读工作区**只读不改；
- 任务达到其「验收标准」后，再标记该任务完成；
- 每完成一项子任务，生成一份任务报告 `docs/dev-docs/<开发序号>/task-report/<编号>-<任务标题>.md`，开发序号取该任务所属开发文档的序号；报告内容须包含：
  - **修改的信息**：本次改了什么、为何修改（对应任务设计）；
  - **修改的文件与文件内位置**：文件路径及具体位置（行号、函数名或段落）；
  - **检查结果**：对照本任务「验收标准」逐项核对的结论；
- 每完成一项任务，立即提交一次 commit：提交信息由该任务内容总结而来，长度不超过 128 字符；任务报告随该任务的 commit 一并提交；
- 每次 commit 后随即执行一次 push。

全部任务完成且均已提交、push 后，进入第 4 步。

### 4. 函数的编写

函数 / 方法的编写遵循函数的设计规则。

**参考文件**：本 Skill 附带 `references/function-design-rules.md`（公有接口设计规范、伪代码实例、校验规则）。此处仅**显式声明其存在**；**仅在编写函数时才读取该文件内容**，其余阶段不展开其正文。

**调用关系规则**：本 Skill 附带 `references/call-relationship-rules.md`（同模块 / 跨模块的方法调用方式与依赖注入约束）。此处仅**显式声明其存在**；**仅在编写方法间的调用时才读取该文件内容**，其余阶段不展开其正文。

**资源生命周期规则**：本 Skill 附带 `references/resource-lifecycle-rules.md`（对象销毁时独占资源的释放责任、释放顺序与借用 / 共享引用处理）。此处仅**显式声明其存在**；**仅在编写对象销毁、资源获取或释放相关代码时才读取该文件内容**，其余阶段不展开其正文。

### 5. Rust 项目的额外约束

实现语言为 Rust 时，还须遵循 Rust 全局约束。

**参考文件**：本 Skill 附带 `references/rust-global-constraints.md`。此处仅**显式声明其存在**；**仅在编写 Rust 代码时才读取该文件内容**，其余阶段不展开其正文。

其他语言暂不提供额外约束文件，沿用第 4 步的函数设计规则。

### 6. 校验

全部任务完成后，逐项检查以下内容：

- `task-list/` 下每个任务文件在 `task-report/` 下都有同名任务报告，且报告非空，覆盖「修改的信息」「修改的文件与文件内位置」「检查结果」三项；
- 每个任务均已对照其「验收标准」通过，且改动只落在任务声明的读写工作区与 `task-report/`；
- 每个任务都有对应 commit，且均已 push。

**校验脚本**：本 Skill 附带 `evals/verify_artifacts.py`（校验任务报告的位置、命名与内容非空，且与 `task-list/` 任务文件一一对应）。此处仅**显式声明其存在**；**仅在本步骤**调用该脚本：

```bash
python evals/verify_artifacts.py docs/dev-docs/<开发序号>
```

全部检查通过后输出产物并结束本阶段；任一项不通过时，对应任务不得标记完成，回到第 3 步修正后重新校验。

## 输入 / 输出

```text
implementer(
  开发序号: string,          // 必填：docs/dev-docs/<开发序号>/，由此定位开发文档、流程图、task-list/ 与 task-report/
  任务分支: string,          // 必填：基于 main 创建的任务分支名，本阶段全部改动提交于此
) -> SkillResult

SkillResult {
  status: "success" | "partial" | "failed",
  artifacts: string[],      // 任务报告路径列表
  errors: SkillError[]
}

SkillError {
  code: string,             // 与「失败处理」的错误码一一对应
  message: string,
  recoverable: boolean
}
```

输出产物：

1. **代码改动**：落在任务声明的读写工作区，对应 `task-list/` 中各任务文件。
2. **任务报告** `docs/dev-docs/<开发序号>/task-report/<编号>-<任务标题>.md`：与任务文件一一对应，含「修改的信息」「修改的文件与文件内位置」「检查结果」。
3. **commit 记录**：每个任务一次 commit，提交信息不超过 128 字符，任务报告随 commit 提交，完成后随即 push。

## 失败处理

| 失败场景             | 判定条件                                                            | 处理动作                                                                            |
| ---------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 开发文档或流程图缺失       | `docs/dev-docs/<开发序号>/` 下不存在 `<标题>开发文档.md` 或 `<标题>流程图.md`，或内容为空 | 中断，不改动代码；回到 `dev-doc-writer` 阶段补齐（`DEV_DOC_MISSING`）                            |
| 任务清单或执行顺序缺失      | `task-list/` 下不存在 `执行顺序.md`，或其中引用的任务文件缺失                        | 中断，不改动代码；回到 `task-planner` 阶段补齐（`TASK_LIST_MISSING`）                            |
| 开发序号无法确定         | 无法从任务所属开发文档目录确定 `<开发序号>`，或与 `task-list/` 目录不一致                  | 中断；使用 `AskUserQuestion` 向人类确认后继续（`SEQ_MISSING`）                                 |
| git 或 gh 不可用     | `git status` 或 `gh auth status` 报错，或 `main` 分支不可用               | 中断并保留原始报错；提示人类配置 git / gh 后重试，禁止跳过提交或 push（`GIT_UNAVAILABLE`）                   |
| 分支创建失败           | 从 `main` 创建任务分支的命令非零退出                                          | 中断并保留原始报错；查明原因（分支已存在、工作区不干净等）后重试，禁止在 `main` 上直接提交（`BRANCH_CREATE_FAILED`）       |
| 改动越界             | 改动出现在只读工作区、任务声明的工作区之外或 `task-report/` 之外                        | 中断；回退越界改动后重新实现该任务（`OUT_OF_SCOPE_CHANGE`）                                        |
| 验收标准未通过          | 任务「验收标准」中任一项核对不通过                                               | 不得标记该任务完成；修正实现后重新验收（`ACCEPTANCE_FAILED`）                                        |
| commit 或 push 失败 | git / gh 命令非零退出，或提交钩子失败                                         | 中断并保留原始报错；修复问题后新建 commit，禁止 `--amend`、`--no-verify`；push 失败同样不得跳过（`GIT_FAILED`） |
| 产物校验未通过          | 「6. 校验」中任一项不满足，或 `verify_artifacts.py` 以退出码 1 结束                | 本阶段不得收尾；按校验结果回到第 3 步修正后重新校验（`VALIDATION_FAILED`）                                |

## 示例

### 示例 1：按清单实现两个任务（成功）

输入：

```text
开发序号：001
任务分支：feat/001-order
```

关键步骤：读取 `docs/dev-docs/001/订单系统开发文档.md`、`订单系统流程图.md` 与 `task-list/执行顺序.md` → 从 `main` 创建 `feat/001-order` → 依次实现「001 创建订单表及索引」「002 实现订单创建校验」，各生成同名任务报告并 commit、push → 运行 `verify_artifacts.py` 校验通过。

输出：

```text
status: success
artifacts: [
  "docs/dev-docs/001/task-report/001-创建订单表及索引.md",
  "docs/dev-docs/001/task-report/002-实现订单创建校验.md"
]
errors: []
```

### 示例 2：任务清单缺失（失败）

输入：

```text
开发序号：001
任务分支：feat/001-order
```

输出：

```text
status: failed
errors: [
  { code: "TASK_LIST_MISSING", message: "docs/dev-docs/001/task-list/ 下不存在 执行顺序.md，已暂停", recoverable: true }
]
处理动作：中断；回到 task-planner 阶段补齐任务清单后再进入本阶段
```
