# task-planner

把已定稿的开发文档，转成一份**可执行、可排序、可验收、可追踪**的任务文件组。

目标不是「把设计文档切成几段」，而是让每个任务都足够原子、可执行，且能被排序与验收。

## 必要前提

1. **奥卡姆剃刀**：如无必要，勿增实体。只拆出完成需求真正需要的任务，不添加需求之外的任务、字段或章节。
2. **每个任务必须声明其工作区**：每个任务都要写明它读写或只读的具体目录 / 文件，作为任务边界的一部分；没有工作区的任务视为未完成。

## 工作流程

### 1. 读取开发文档

输入为已定稿的开发文档与流程图，即 `docs/dev-docs/<开发序号>/` 下的 `<标题>开发文档.md` 与其同目录的 `<标题>流程图.md`。若开发文档不存在或未定稿，先回到 `dev-doc-writer` 阶段，不自行脑补设计。

### 2. 拆出原子任务

按「核心拆分规则」拆出任务，每个任务必须同时满足：

| 标准 | 含义 |
| --- | --- |
| 原子 | 一个任务只做一件事 |
| 可执行 | Agent 能依据任务描述直接动手 |
| 可验收 | 有明确的通过标准 |
| 有依赖 | 明确前置任务与后置任务 |
| 有边界 | 能对应到模块、文件、接口、表结构或配置项 |

**资源生命周期规则**：本 Skill 附带 `references/resource-lifecycle-rules.md`（销毁时独占资源的释放责任、释放顺序与借用 / 共享引用约束）。此处仅**显式声明其存在**；**仅在判断是否需要资源释放任务时才读取该文件内容**，其余阶段不展开其正文。

### 3. 为每个任务建立独立任务文件

一个任务一个文件，内容从开发文档中摘录本任务要实现的**函数、结构体、数据库表**，与本任务无关的设计元素不写入。依赖关系必须在**本阶段**显式产出，禁止循环依赖。

**每个函数条目必须附带函数内部流程图**：依据开发文档中该函数的功能描述（职责说明、入参、返回值、错误返回、调用关系）与同目录流程图中的「函数内运行流程图」，为该函数单独设计 Mermaid 流程图并写入该条目。流程图须覆盖开始 / 结束、分支判断、错误返回与函数调用方向；不得照搬整份流程图、不得多个函数共用一个流程图。

> 示例：若开发文档的「函数内运行流程图」描述的是入口函数 A 的完整流程，而任务中的函数 B 是 A 内部调用的一个校验函数，则 B 的流程图只描述 A 传递到 B 的参数如何被校验、校验失败返回什么错误、校验通过后返回什么，不重复 A 的其余步骤。

**参考模板**：本 Skill 附带 `assets/task-template.md`。此处仅**显式声明其存在**；**仅在制作任务文件时才读取该文件内容**并据其结构撰写，其余阶段不展开其正文。

- 目录：`docs/dev-docs/<开发序号>/task-list/`，开发序号与本次拆分的开发文档、流程图一致；
- 命名：`<编号>-<任务标题>.md`；
- 每个文件最开头为 JSON 头，声明 `编号`（字符串）与 `依赖`（数组，无依赖填 `[]`）。

### 4. 生成执行顺序

执行顺序由脚本对任务文件中的「依赖」做拓扑排序得到，**不得agent自行排序**。

**脚本**：本 Skill 附带 `scripts/topo_sort.py`。扫描任务目录、构建有向图、检测循环依赖、输出执行顺序文件：

```bash
python scripts/topo_sort.py docs/dev-docs/<开发序号>/task-list -o docs/dev-docs/<开发序号>/task-list/执行顺序.md
```

若存在循环依赖，脚本报错退出，须回到第 3 步修正依赖后再运行。

### 5. 校验

- 任务目录下每个任务文件都有合法 JSON 头（`编号` 与 `依赖` 数组）、`工作区`、`验收标准`，且实现内容取自开发文档；
- 任务文件中的每个函数条目都附带函数内部流程图，且流程与开发文档描述的功能、同目录流程图一致（不照搬整份流程图、不遗漏错误返回与分支）；
- 执行顺序文件覆盖全部任务，且不存在循环依赖。

## 核心拆分规则

**规则 1：依赖优先，禁止循环依赖。**
若任务 B 需要任务 A 的产物，则 A 必须排在 B 之前。依赖须显式建模为 DAG，禁止出现环。

**规则 2：先基础设施，后业务功能。**
常见顺序依次为：

1. 数据模型 / 表结构 / Schema
2. 基础配置、常量、枚举、错误码
3. 公共工具、接口契约、类型定义
4. 核心业务逻辑
5. 接口 / API / UI
6. 集成测试、端到端验证
7. 文档、迁移脚本、运维配置

设计文档中若有数据库变更、公共模块、权限模型、路由框架，这些通常要前置。

**规则 3：一个任务只改一个清晰边界。**
禁止「完成后端 / 完成前端 / 完成数据库」这类跨边界大任务，应拆为「创建订单表及索引」「实现订单创建接口」「实现订单查询接口」等。若一次改动同时跨数据库、后端、前端，必须拆成多个任务。

**规则 4：每个任务必须有验收标准。**
验收标准要可观察、可执行，禁止写「完成开发」「功能正常」这类不可判定的表述。

**规则 5：参考流程图拆分。**
依据同目录的总流程图的状态流转确定任务边界与先后次序，不脱离流程图自行划分。

## 执行顺序生成

排序流程：提取任务节点 → 由任务文件的「依赖」声明前置关系 → 构建有向图 → 检测是否存在环 → 拓扑排序 → 对同一层级的无依赖任务，再按风险、模块、文件边界做二次排序。

依赖关系必须由拆分阶段显式产出；排序脚本只负责排序，不推断依赖。

## 输出产物

产物均位于 `docs/dev-docs/<开发序号>/task-list/`：

1. **任务文件** `<编号>-<任务标题>.md`：一个任务一个文件，含编号、任务、工作区、依赖、产出、验收标准，以及从开发文档摘录的实现内容（函数、结构体、数据库表）；每个函数条目另附依据开发文档与同目录流程图设计的函数内部流程图。
2. **执行顺序文件** `执行顺序.md`：由脚本拓扑排序生成的线性任务序列，供 agent 按序执行。

## 约束

- 产物只写入 `docs/dev-docs/<开发序号>/task-list/`，不新增其他文件或目录。
- 任务文件中的实现内容必须取自开发文档，不得自行新增设计；函数内部流程图只能依据开发文档的功能描述与同目录流程图设计，不得编造开发文档未描述的分支、错误或调用。
- 缺少函数内部流程图的任务文件不得定稿。
- 存在循环依赖时不得输出执行顺序，必须先修正依赖。
- 任务粒度以「能独立验证」为准；验收标准不可判定的任务不得定稿。
