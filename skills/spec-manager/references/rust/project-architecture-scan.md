# 项目目录架构扫描与描述口径

本文件供 `spec-manager` 在第 3 步扫描并描述项目目录架构、写入 `docs/开发规范/项目目录架构规范.md` 时使用。

## 一、扫描范围

- 从仓库根目录开始，优先描述顶层业务目录，再逐层展开到有独立职责的子目录；
- 忽略以下目录：`.git/`、`target/`、`vendor/`、`node_modules/`、各类构建与缓存目录、IDE 配置目录；
- 只描述**长期存在**的目录，不描述某次开发临时创建的目录（如 `docs/dev-docs/<序号>/` 内部结构按约定一笔带过）。

## 二、职责描述口径

写入规范文档时同时给出两部分：先用目录树直观展示层级结构，再用职责表逐项说明。目录树的每个节点附一句话职责注释。

每个目录一行，写清三件事，缺一不可：

1. **职责**：这个目录负责什么，一句话说明，不写「存放相关文件」这类空泛描述；
2. **内容类型**：主要存放的内容形态（如「模块源码」「集成测试」「构建脚本」「文档」）；
3. **依赖方向**：允许依赖哪些目录、禁止依赖哪些目录（有明确约束时写，无约束时写「无特别约束」）。

示例：

| 目录 | 职责 | 内容类型 | 依赖方向 |
| --- | --- | --- | --- |
| `src/` | 库源码与对外 API | Rust 模块源码 | 可依赖 `src/common/`；禁止依赖 `tests/` |
| `tests/` | 集成测试 | 测试用例与测试辅助代码 | 只依赖 `src/` 的公有 API |

## 三、无目录架构时的推荐方案

项目尚无目录架构规划时，先给出推荐方案，再用 `AskUserQuestion` 让用户选择。推荐方案至少包含：

- 一个最小可用的目录骨架（源码、测试、文档、脚本各自的落点）；
- 每个目录的一句话职责；
- 说明推荐方案的取舍（为什么这样分，不采用其他分法的原因）。

`AskUserQuestion` 的选项至少包含：

1. 「采用推荐方案」；
2. 「在现有目录上补充说明」（保留现有结构，只补职责描述）；
3. 「由我描述」（用户通过「Other」给出自己的方案）。

用户选择后，按其选择写入规范文档；方案未确认前禁止写入。

## 四、更新已有规范时的处理

- 只更新职责发生变化或新增 / 删除的目录条目；
- 记录「原职责 → 新职责 → 变更原因」，供第 4 步写入迁移信息；
- 文档内只保留最新目录架构，不保留历史版本。
