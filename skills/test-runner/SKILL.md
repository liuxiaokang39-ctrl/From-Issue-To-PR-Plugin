# test-runner

按 `test-planner` 产出的测试流程文档执行三层测试，如实记录执行过程与结果，并处理失败。本 Skill 不重新设计测试流程。

## 必要前提

1. **全部场景通过**：单元白盒、集成白盒、真实部署黑盒测试的所有场景必须通过。禁止虚构、推测或复用旧结果；未实际执行的场景不得标记为通过。
2. **禁止静默吞错**：执行中的报错、失败、超时与异常必须原样暴露并如实记录；不得用捕获后忽略、空断言、跳过标记或降低断言的方式掩盖失败。
3. **测试与源码隔离**：测试代码放在独立的测试目录或测试文件中，不写入生产源码；不为测试在生产源码中添加钩子、测试分支或额外导出。
4. **公开性不变**：修复过程中不得修改函数 / 方法的公开属性。
5. **奥卡姆剃刀**：不引入与真实实现无关的测试机制、mock 框架或抽象层；项目已有测试框架能满足需求时，不引入新框架。

## 工作流程

### 1. 读取测试流程与真实实现

- 读取 `docs/test-process/<开发文档序号>/` 下的 `1-单元白盒测试流程.md`、`2-集成白盒测试流程.md`、`3-真实部署黑盒测试流程.md`；
- 读取流程文档「工作区范围」中列出的被测文件与函数，确认当前实现；
- 流程文档缺失、场景缺少可判定的期望结果、或文档与真实实现不一致时，停止该场景并回退到 `test-planner` 重新设计；不得擅自改写期望结果使测试通过，也不得以执行结果倒推期望。

### 2. 按顺序执行测试

- 通过 shell（shell MCP / 终端）按「单元白盒 → 集成白盒 → 真实部署黑盒」的顺序执行，每份文档内按场景编号顺序执行；
- 若当前环境没有可用的 shell 执行能力，先启用或安装 shell MCP；仍不可用时提示人类安装；
- 缺少测试框架、编译器、运行时或依赖时，按流程文档「测试所需外部资源」补齐；安装失败则提示人类安装，不得跳过或伪造结果；
- 真实部署黑盒场景未经人类审核确认的，不得执行；
- 每个场景记录实际执行的命令、实际输出与通过 / 失败结论；失败或异常时必须保留完整错误信息，禁止静默吞错；
- 测试代码写入项目约定的独立测试目录（如 `tests/`、`__tests__/` 等）或独立测试文件，不写入生产源码。

### 3. 处理失败

仅当失败属于以下两种情形之一时，才允许修改工作区代码：

- 代码逻辑正常，仅因入参校验缺失或未覆盖测试样例导致失败；
- 代码逻辑正常，仅因返回值格式与预期不符导致失败。

修复须保持函数公开属性不变，只做满足测试所需的最小改动。修改后重新执行受影响场景，并重新执行同文档内的关联场景与后序测试，不得只跑失败场景就宣称通过。

若失败由设计逻辑本身导致，即按开发流程图的状态流转不可能达到测试目标，则不得修改代码迁就测试；应在 `docs/test-report/<测试流程序号>/failure-report/` 下生成 `<序号>-测试未通过报告.md`（同一流程下存在多份失败报告时按序号递增区分），并按失败报告模板记录失败类型与场景、命令与结果、期望与实际、设计原因及为何无法通过测试目标。

**参考模板**：本 Skill 附带 `references/test-fail-report-template.md`。此处仅**显式声明其存在**；**仅在生成失败报告时才读取该模板**，其余阶段不展开其正文。

### 4. 生成测试报告

- 全部场景实际执行并通过（含第 3 步修复后复测通过）时，在 `docs/test-report/<测试流程序号>/` 下生成 `测试报告.md`，记录执行环境、各场景的命令与实际结果、通过结论；
- 存在设计逻辑原因导致的失败时，按第 3 步在 `failure-report/` 下生成失败报告；同一流程中已通过的场景仍按上一条生成 `测试报告.md`；
- 报告内容必须与执行时的实际命令和输出一致，不得事后补写、润色或虚构。

**参考模板**：本 Skill 附带 `references/test-pass-report-template.md`。此处仅**显式声明其存在**；**仅在生成通过报告时才读取该模板**，其余阶段不展开其正文。失败报告模板见第 3 步。

### 5. 汇报结果

向人类如实汇报每份流程文档的场景总数、通过数、失败数与未执行数、失败项的处理结论，以及通过报告与失败报告的存放路径。未执行数必须为 0 且全部场景实际通过后，本阶段才结束；禁止把未执行或跳过的场景计入通过。

## 约束

- 不得虚构测试结果；未实际执行的场景不得标记为通过。
- 不得静默吞错；任何错误、异常与超时必须暴露并记录。
- 不得修改函数公开属性；不得为测试在生产源码中加入钩子或测试分支。
- 不得引入与真实实现无关的测试机制；项目已有测试框架可用时不引入新框架。
- 不得擅自修改测试流程文档以迁就执行结果；流程有问题时回退到 `test-planner`。
- 属于设计逻辑原因导致的失败，不得改代码迁就测试，只能产出失败报告。
- 除 `docs/test-report/<序号>/` 下的通过报告与 `failure-report/` 下的失败报告，以及按项目约定放置的测试代码外，不新增其他文件或目录。
