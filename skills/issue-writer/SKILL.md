# issue-writer

把用户口述的模糊需求，通过对话收敛为一份可评审的 Issue。

## 必要前提

1. **奥卡姆剃刀**：如无必要，勿增实体。只保留用户确认过的需求，不添加未经确认的需求、字段或章节。
2. **信息不足必须提问**：凡「是否需要该需求」「需求本身」「期望行为」「期望结果」存在不明确处，一律向用户提问，由用户决定；禁止自行脑补、假设或替用户拍板。

## 工作流程

### 1. 明确需求出现的背景

先向用户确认：这个需求因何而来、要解决什么问题、当前状况如何、涉及哪些使用方。

### 2. 明确具体需求，并列表

- 先逐条与用户确认需求**是否真实需要**（必要性、真伪），再谈细节。
- 把确认后的需求整理为编号列表。

### 3. 明确每项需求的期望行为与期望结果

对列表中每一项需求，与用户确认：

- **期望行为**：在什么场景下、系统应如何表现；
- **期望结果**：如何判断它已达成，即可观察、可验证的判定依据。

提问节奏：先确认该需求是否需要 → 再列出这条需求中尚不清楚的部分，逐项向用户提问。

### 4. 制作需求报告（Issue）

- 与用户对齐后，把最新需求汇总为一份 Issue；Issue 正文按第 5 点声明的模板组织。
- **报告只包含最新需求**。如果对齐后需要更新报告，禁止把已被推翻、已过时的旧需求迁移进报告——过时需求一律不写入。

### 5. 创建 Issue 并本地留档

**参考模板**：本 Skill 附带一份 Issue 样例模板 `references/issue-template.md`。此处仅**显式声明其存在**；**仅在制作 Issue 时才读取该文件内容**并据其结构撰写，其余阶段不展开其正文。

**参考命令与提交规范**：本 Skill 附带 `references/GitHub-CLI.md`（gh 命令参考，含 `gh issue create`）与 `references/GitHub-submit.md`（git 提交规范与 Git 安全约束）。此处仅**显式声明其存在**；**仅在创建 Issue、需要使用 gh 或 git 命令时才读取这些文件内容**，其余阶段不展开其正文。

先判断项目远端仓库的类型，再决定 Issue 创建在哪个仓库：

- 远端是**主仓库** → 在远端主仓库创建 Issue；
- 远端是 **fork 仓库** → 在 fork 仓库创建 Issue。
- 无法判断远端类型或没有远端仓库时，向用户询问后再执行。

用 `gh issue create` 创建 Issue。无论哪种情况，都在本地留档：

- 目录：`docs/requirement-issue/`
- 文件名：`<仓库名>-<issue编号>-issue.md`（仓库名取实际创建 Issue 的仓库名，如 `From-Issue-To-PR-Skill-12-issue.md`）

## 约束

- 除上述产物外，不新增其他文件或目录。
- 未经用户确认的内容不得写入 Issue；未决项一律列入「待确认问题」，不得写成已确认。
