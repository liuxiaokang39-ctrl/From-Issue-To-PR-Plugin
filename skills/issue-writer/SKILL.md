# issue-writer

把用户口述的模糊需求，通过对话收敛为一份可评审的 Issue，并在远端仓库创建、本地留档，供评审后进入开发阶段。

## 适用场景

- 适用：用户给出模糊、零散或未成型的需求描述，需要先收敛收敛再产出 Issue；用户提到「需求确认」「整理需求」「写/创建 Issue」「把需求做成 Issue」等说法，以及需求列表、期望行为、期望结果、范围边界等输入形态。
- 不适用：需求已完全明确、无需对话收敛；Issue 的评审讨论；以及 /docs 之外的普适文档编写（由其他 Skill 或人工处理）。

## 必要前提

1. **需求已收敛并确认**：已通过对话与用户逐条确认需求清单、每项需求的期望行为与期望结果、范围边界；未决项已列入「待确认问题」。不满足时必须继续提问，不得进入制作 Issue 阶段。
2. **远端仓库类型可判断**：能确认项目远端是主仓库还是 fork 仓库；无法判断或没有远端仓库时，须先向用户询问。
3. **开发序号已确认**：本地留档目录 `docs/dev-docs/<开发序号>/` 中的 `<开发序号>` 已由用户确认。未确认时先向用户询问。
4. **gh CLI 可用**：执行 `gh auth status` 能确认已登录认证；未安装或未认证时，向用户确认是安装/认证后继续，还是降级为仅本地留档。

## 执行约束

- 必须：只保留用户确认过的需求，不添加未经确认的需求、字段或章节（奥卡姆剃刀）。
- 必须：凡「是否需要该需求」「需求本身」「期望行为」「期望结果」存在不明确处，一律向用户提问并由用户决定；禁止自行脑补、假设或替用户拍板。
- 禁止：把已被推翻、已过时的旧需求迁移进 Issue——报告只包含最新需求。
- 禁止：除「远端 Issue 与本地留档文件」外，新增其他文件或目录。
- 只能修改：通过 `gh issue create` 在已确认的远端仓库创建 Issue；本地留档写入 `docs/dev-docs/<开发序号>/` 目录。

**参考文件**：本 Skill 附带三份参考材料，此处仅**显式声明其存在**，不展开其正文：

- `assets/issue-template.md`（Issue 正文结构模板）：**仅在制作 Issue 时**读取该文件内容并据其结构撰写；
- `references/GitHub-CLI.md`（gh 命令参考，含 `gh issue create`）：**仅在创建 Issue、需要使用 gh 命令时**读取；
- `references/GitHub-submit.md`（git 提交规范与 Git 安全约束）：**仅在创建 Issue、需要进行 git 操作时**读取。

## 工作流程

### 第 1 步：确认背景、目标与范围（合并「背景」与「范围边界」）

与用户逐个确认：

- **为什么做**；
- **解决什么问题**；
- **提供什么功能**；
- **本期做什么、不做什么**（范围边界）。

### 第 2 步：逐条确认需求与验收标准（合并「需求列表」与「期望行为/期望结果」）

对每一条需求，与用户逐项确认：

- **这条需求是必要需求还是可选需求**；
- **使用场景是什么**（什么条件下触发）；
- **系统应如何表现**（行为）；
- **如何验证达成**（可观察、可验证的结果）。

### 第 3 步：汇总 Issue 并请用户确认

- 只写最新确认的需求；
- 不允许有未确认内容；
- 用户确认正文后，再创建 Issue，并根据用户意见决定是否在远端仓库创建 Issue。

### 第 4 步：判断仓库、创建 Issue、本地留档并回传链接

创建前判断主仓库/fork：

- 主仓库 → 在主仓库创建；
- fork 仓库 → 在被 fork 的仓库创建；
- 无法判断远端类型或没有远端仓库时，向用户询问后再执行。

用 `gh issue create` 创建 Issue。留档规则：

- 目录：`docs/dev-docs/<开发序号>/`（`<开发序号>` 由用户确认）；
- 文件名：`<仓库名>-<issue编号>-issue.md`（仓库名取实际创建 Issue 的仓库名，如 `From-Issue-To-PR-Skill-12-issue.md`）；
- 回传 Issue 链接。

## 输入 / 输出

```text
issue_writer(
  模糊需求: string,                            // 必填：用户口述的原始需求
  需求列表: Requirement[],                     // 必填：与用户逐条确认后的需求（含是否必需）
  期望行为与期望结果: Map<编号, {行为, 结果}>, // 必填：每项需求的行为与可验证结果
  范围边界: string,                            // 可选：确认「做什么 / 不做什么」后写入
  远端仓库类型: "main" | "fork" | null,        // 可选：无法判定时先询问用户
  开发序号: number,                            // 必填：由用户确认的本次开发序号
) -> SkillResult

SkillResult {
  status: "success" | "partial" | "failed",
  artifacts: string[],        // 远端 Issue 地址 + 本地留档文件路径
  errors: SkillError[]
}

SkillError {
  code: string,               // 与「失败处理」的错误码一一对应
  message: string,
  recoverable: boolean
}
```

## 失败处理

| 失败场景 | 判定条件 | 处理动作 |
| --- | --- | --- |
| 需求信息不足 | 存在未确认的需求、期望行为或期望结果，却直接进入制作 Issue | 中断；逐条向用户提问补齐，补齐前不得写入 Issue（`INPUT_INCOMPLETE`） |
| gh 认证失败 | `gh auth status` 未认证，或 `gh issue create` 因认证报错 | 中断并保留原始报错；询问用户是安装/认证后重试，还是降级为仅本地留档（`AUTH_FAILED`） |
| `gh issue create` 失败 | 命令非零退出、网络或权限错误 | 重试一次；仍失败则中断，保留原始报错，仅完成本地留档，并提示用户改为手动创建（`CREATE_FAILED`） |
| 远端仓库类型无法判断 | 无法确认主仓库或 fork，或没有远端仓库 | 中断；向用户询问目标仓库后再执行（`REPO_UNKNOWN`） |
| 开发序号未确认 | 用户未提供 `<开发序号>` | 中断；先向用户确认序号后再留档（`SEQ_MISSING`） |

## 示例

### 示例 1：成功收敛并创建 Issue

输入：

```text
模糊需求：登录成功后展示最近一周的操作记录
需求列表：1. 登录后展示操作记录（必需）；2. 记录用户操作日志（必需）
期望行为与期望结果：1. 登录成功后在首页展示最近一周操作，判定=列表含当日与最近7天数据；
                     2. 记录关键操作日志，判定=日志文件有对应记录
范围边界：不涉及操作明细导出
远端仓库类型：main
开发序号：12
```

输出：

```text
gh issue create 成功，issue #12
artifacts: [
  "https://github.com/<owner>/From-Issue-To-PR-Skill/issues/12",
  "docs/dev-docs/12/From-Issue-To-PR-Skill-12-issue.md"
]
status: success
errors: []
```

### 示例 2：需求信息不足（失败）

输入：

```text
模糊需求：给系统加个导出功能
需求列表：1. 导出报表（是否必需？）
期望行为与期望结果：（未确认）
```

输出：

```text
status: failed
errors: [
  { code: "INPUT_INCOMPLETE", message: "期望行为与期望结果未确认，已暂停", recoverable: true }
]
处理动作：中断；逐条向用户提问确认导出场景、期望结果与是否必需后再继续
```
