# SKILL内容开发规范

本规范规定 `SKILL.md` 的内容格式，所有 Skill 的 `SKILL.md` 必须依据本规范编写。规范中的「必须 / 不得 / 应当 / 可以」按以下含义使用：

- **必须 / 不得**：强制要求，违反即视为不合规；
- **应当**：默认要求，确有必要偏离时需在正文中说明理由；
- **可以**：可选，按 Skill 实际需要决定。

适用范围：

- 新建 Skill 的 `SKILL.md` 立即适用本规范；
- 存量 Skill 的 `SKILL.md` 在下一次重构时对齐本规范，本次不批量修改。

## 文件整体结构

`SKILL.md` 由上至下固定为两部分，不得调整顺序、不得插入其他顶层结构：

1. **YAML Frontmatter**：文件顶部的元数据块，决定 Agent「是否加载这个 Skill」；
2. **正文**：Skill 的执行说明，决定 Agent「如何执行这个 Skill」。

正文的二级标题必须按以下顺序出现，且不得缺省：

| 顺序 | 章节 | 作用 |
| --- | --- | --- |
| 1 | Skill 名称与概述 | 建立整体认知，划定适用与不适用场景 |
| 2 | 前置条件 | 声明执行前必须满足或检查的条件 |
| 3 | 执行约束 | 声明执行过程中必须遵守的边界 |
| 4 | 工作流程 | 按编号步骤声明执行顺序、每步输入与产物 |
| 5 | 输入 / 输出 | 用类似函数签名的方式约定数据契约 |
| 6 | 失败处理 | 定义异常路径，防止 Agent 自由发挥 |
| 7 | 示例 | 用典型示例校准 Agent 的理解 |

## 一、YAML Frontmatter

`SKILL.md` 以 `---` 分隔的 YAML 元数据块开头，形如：

```yaml
---
name: <skill-name>
description: <做什么 + 何时使用>
---
```

约束：

- 起始与结束的 `---` 必须各占一行，之间只能包含 YAML 元数据；
- Frontmatter 之后必须空一行，再开始正文；
- 字段值中如出现冒号、引号等 YAML 特殊字符，必须使用合规的引号包裹或改写为普通文本，保证 YAML 可解析。

### 1.1 必填字段

| 字段 | 说明 | 约束与建议 |
| --- | --- | --- |
| `name` | Skill 的唯一标识名，用于发现与引用 | 最多 64 字符；仅允许小写字母、数字和连字符；不得以连字符开头或结尾；不得出现连续连字符；必须与所在文件夹名完全一致 |
| `description` | 清晰描述 Skill 做什么以及何时使用 | 最多 1024 字符；必须包含帮助 Agent 识别相关任务的关键词；这是 Agent 决定是否触发 Skill 的首要依据，应当详细且具有主动性（pushy），主动列出触发场景 |

`description` 推荐写法：

- 前半句写「做什么」，用动词开头，覆盖核心能力；
- 后半句写「何时使用」，列出典型任务、输入形态与用户可能的说法；
- 避免只写抽象定位（如「一个用于文档处理的 Skill」），必须给出可被匹配的关键词。

### 1.2 可选字段

| 字段 | 作用 | 说明 |
| --- | --- | --- |
| `license` | 许可证信息 | 如 `MIT`、`Apache-2.0`，指明他人可以如何使用和修改该 Skill |
| `compatibility` | 环境兼容性要求 | 最多 500 字符，说明需要的运行环境、依赖或工具（如特定 Python 版本、CLI 工具） |
| `metadata` | 自定义扩展元数据 | 键值对映射，可存放作者、版本、维护者等规范之外的额外信息 |
| `allowed-tools` | 预授权工具列表 | 实验性功能，用空格分隔的 Glob 模式，限制 Skill 可以调用哪些工具 |

可选字段仅在确有需要时声明，不得为「占位」写入空值。

### 1.3 最小有效示例

```yaml
---
name: pdf-processing
description: Extracts text and tables from PDF files, fills forms, and merges PDFs. Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction.
---
```

## 二、正文部分

### 2.1 Skill 名称与概述

- 一级标题必须为 `# <name>`，与 Frontmatter 的 `name` 完全一致；
- 标题下用一到三句话说明 Skill 的目的、核心价值与在整体链路中的位置；
- 必须显式区分适用与不适用场景，避免 Agent 在边界任务上误触发。

推荐结构：

```markdown
# <skill-name>

<一句话说明这个 Skill 解决什么问题、产出什么。>

## 适用场景

- 适用：<典型任务与输入形态>
- 不适用：<明确交给其他 Skill 或人工处理的任务>
```

### 2.2 前置条件

列出执行该 Skill 前必须满足的条件或必须执行的检查步骤。前置条件必须可判定，不得写成模糊描述。

要求：

- 每条前置条件都必须能被检查（文件存在、参数已确认、依赖已安装、分支状态正确等）；
- 条件不满足时必须给出明确的去向（回到上一阶段、向用户提问、终止执行），与「失败处理」保持一致；
- 前置条件中出现的外部产物，必须写清其位置与命名规则。

### 2.3 执行约束

列出执行该 Skill 时必须满足的约束条件，用于划定 Agent 的行为边界。

要求：

- 使用「必须 / 不得 / 只能」等明确措辞，避免「尽量」「建议」等弱约束；
- 约束必须可验证，例如限定可写入的目录、可修改的工作区、禁止的操作；
- Skill 附带参考文件时，在此章写明「文件存在」与「何时读取」，不展开参考文件正文。推荐写法：

```markdown
**参考文件**：本 Skill 附带 `references/<文件名>.md`（<内容概述>）。此处仅**显式声明其存在**；**仅在 <触发条件> 时才读取该文件内容**，其余阶段不展开其正文。
```

### 2.4 工作流程

按执行先后顺序，把 Skill 的完整执行过程拆成编号步骤，用于指导 Agent 逐步推进。

要求：

- 必须使用编号步骤（如 `1.`、`2.`）表达顺序，不得用无序列表代替；
- 每个步骤只说清一件事，写清该步的目标、使用的输入、执行的动作与产出的中间结果；
- 每个步骤必须写明进入下一步的判定条件；存在条件分支、等待人类确认或回流上一阶段时，必须在该步骤写明触发条件与去向；
- 引用 `references/`、`scripts/`、`assets/` 时，必须在该步骤显式声明其存在，并写明读取或调用的时机，不展开其正文；
- 步骤中出现的路径、文件名与字段名必须与「输入 / 输出」保持一致。

推荐结构：

````markdown
## 工作流程

### 1. <步骤名称>

<该步骤的目标、输入与动作。>

- <动作项>
- **参考文件**：本 Skill 附带 `references/<文件名>.md`（<内容概述>）。此处仅**显式声明其存在**；**仅在 <触发条件> 时才读取该文件内容**，其余阶段不展开其正文。

### 2. <步骤名称>

<该步骤的目标、输入与动作；写明进入下一步的判定条件。>
````

### 2.5 输入 / 输出

用类似函数签名的方式，明确 Skill 接收的输入格式与产生的输出结构，确保 Agent 与调用方都能准确解析。

要求：

- 输入必须逐个列出参数名、类型、是否必需、默认值与含义；
- 输出必须列出成功产物与失败结果的结构，产物的路径、文件名与格式必须写清；
- 存在多种输出形态时（如成功 / 部分成功 / 失败），必须分别声明；
- 签名中的字段名必须与正文其他章节、脚本参数、模板占位符保持一致。

推荐结构：

```text
skill_name(
  input_a: string,          // 必填：<含义>
  input_b: string | null,   // 可选：<含义>，缺省 <默认行为>
) -> SkillResult

SkillResult {
  status: "success" | "partial" | "failed",
  artifacts: string[],      // 产物路径列表
  errors: SkillError[]
}

SkillError {
  code: string,             // 与「失败处理」的错误码一一对应
  message: string,
  recoverable: boolean
}
```

### 2.6 失败处理

明确定义失败路径，防止 Agent 在异常情况下「自由发挥」。失败处理必须覆盖以下三类场景：

| 类别 | 典型场景 | 处理要求 |
| --- | --- | --- |
| 输入无效 | 参数缺失、文件不存在、格式不符合约定 | 必须说明如何判定与如何提示，不得自行补全或猜测输入 |
| 工具调用失败 | 命令报错、脚本非零退出、网络或权限失败 | 必须说明是重试、降级还是终止；终止时须保留原始报错 |
| 条件不满足 | 前置条件缺失、依赖未就绪、状态冲突 | 必须给出明确去向（回到指定阶段、询问用户、终止） |

要求：

- 使用表格逐项声明「失败场景 → 判定条件 → 处理动作」，判定条件必须客观可查；
- 处理动作必须包含：是否中断执行、是否保留现场、是否需要用户确认；
- 同一失败场景的处理方式在全文必须一致，不得在「前置条件」「执行约束」「失败处理」之间出现矛盾；
- 不得出现「视情况而定」「自行判断」等无约束表述。

推荐结构：

| 失败场景 | 判定条件 | 处理动作 |
| --- | --- | --- |
| `<场景>` | `<可观察条件>` | `<中断 / 继续 / 回退>`；`<提示内容或去向>` |

### 2.7 示例

提供典型的输入输出示例，或展示在不同场景下如何选用不同方法，帮助 Agent 更准确地理解指令。

要求：

- 至少包含一个完整成功示例：输入 → 关键步骤 → 输出；
- 存在分支或多种方法时，必须补充对应示例，并说明选择依据；
- 存在失败路径时，应当补充一个失败示例，覆盖错误码与处理动作；
- 示例中的路径、字段、文件名必须与正文契约一致，不得出现正文未声明的字段。

推荐结构：

````markdown
### 示例 1：<场景>

输入：

```text
<参数清单>
```

输出：

```text
<产物路径与结果摘要>
```
````

## 三、完整模板

新建 `SKILL.md` 时应当以下面的骨架为起点，按实际情况填充，不得删除任何必需章节：

````markdown

description: <做什么 + 何时使用；包含触发关键词与典型场景，不超过 1024 字符>

- 不适用：<明确交给其他 Skill 或人工处理的任务>

1. **<前提名称>**：<可判定的条件>；不满足时 <去向>。
2. **<前提名称>**：<可判定的条件>；不满足时 <去向>。
````

## 四、合规检查清单

提交或评审 `SKILL.md` 时，必须逐项核对：

- [ ] Frontmatter 以 `---` 起止，YAML 可解析；
- [ ] `name` 与所在文件夹名完全一致，且满足字符与连字符规则；
- [ ] `description` 不超过 1024 字符，包含触发关键词与典型使用场景；
- [ ] 一级标题与 `name` 一致；
- [ ] 七个必需章节齐全、顺序正确，没有空章节；
- [ ] 前置条件均可判定，且写明了不满足时的去向；
- [ ] 执行约束使用明确措辞，可写入的范围已限定；
- [ ] 工作流程以编号步骤声明执行顺序，每步写明输入、动作与产物，分支与回流已写明触发条件；
- [ ] 输入 / 输出以签名方式声明，字段名与正文其他章节一致；
- [ ] 失败处理覆盖输入无效、工具调用失败、条件不满足三类场景，且与前置条件无矛盾；
- [ ] 至少包含一个完整成功示例，示例字段均在正文中声明；
- [ ] 附带的参考文件、脚本、模板均被显式声明存在，并写明了读取或调用时机。
