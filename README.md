# From Issue To PR Skill

> 一套从「模糊需求」到「可合并 PR」的 Skill 工作流：确认需求 → 产出开发文档 → 拆分任务并实现 → 测试 → 提交 PR。

## 项目简介

本仓库是一个 **Skill 组仓库**，把软件开发中从需求到提交 PR 的完整链路拆成 6 个可独立调用、也可顺序串联的 Skill。每个 Skill 负责一个阶段，并明确各自的输入与产出物，因此既可以走完整流程，也可以只取用其中一环。

它解决的问题：

- 需求在口头传递中失真，边界不清、验收标准缺失；
- 开发文档滞后于代码，方案与实现脱节；
- 任务拆分粒度不可执行，无法逐项验收；
- 测试与验收标准不对齐，回归范围不明；
- PR 描述缺少上下文，评审需要回溯大量背景。

各阶段的产物默认统一落在使用者项目的 `docs/` 目录下，除非显式指定其他位置。

## 工作流总览

```
issue-writer → dev-doc-writer → task-planner → implementer → tester → pr-creator
   需求确认       开发文档          任务拆分        编码实现      测试验证     提交 PR
```

| 阶段 | Skill | 输入 | 产出物 |
| --- | --- | --- | --- |
| 需求确认 | `issue-writer` | 用户口述需求、项目背景 | 远端仓库中的 Issue + 本地留档：背景与目标、需求列表、每项需求的期望行为与期望结果、范围边界、待确认问题 |
| 开发文档 | `dev-doc-writer` | Issue 内容、代码库上下文 | `docs/dev-docs/` 下的目录结构文档、开发文档（数据结构、函数定义）与配套流程图 |
| 任务拆分 | `task-planner` | 开发文档 | `docs/dev-docs/<序号>/` 下的任务文件（`<编号>-<任务>.md`）与执行顺序文件（`执行顺序.md`） |
| 编码实现 | `implementer` | 任务清单、代码库 | 逐项实现的代码改动 |
| 测试验证 | `tester` | 代码改动、验收标准 | 测试用例 + 测试结果报告（通过/失败项、回归范围） |
| 提交 PR | `pr-creator` | 代码改动、Issue、开发文档、测试报告 | PR 标题与描述（背景、改动摘要、验证方式、影响面、回滚方案） |

产物建议命名：`docs/requirement-issue/<仓库名>-<issue编号>-issue.md`、`docs/dev-docs/<序号>-<标题>开发文档.md` 与 `docs/dev-docs/<序号>-<标题>流程图.md`、`docs/dev-docs/<序号>/<编号>-<任务>.md` 与 `docs/dev-docs/<序号>/执行顺序.md`、`docs/test-report.md`；PR 描述随 PR 一并提交。

## Skill 清单

### `issue-writer` —— 需求确认

- **职责**：把零散、模糊的想法收敛为一份可评审的 Issue。
- **输入**：用户口述的需求、项目背景、相关代码或资料（可选）。
- **产出**：在远端仓库创建 Issue（远端为主仓库时建于主仓库；远端为 fork 时优先建于上游仓库，否则建于 fork），并在本地留档 `docs/requirement-issue/<仓库名>-<issue编号>-issue.md`；内容含背景与目标、需求列表、每项需求的期望行为与期望结果、范围边界（做什么 / 不做什么）、待确认问题清单。
- **关键行为**：先确认需求是否真实需要，再就尚不清楚的部分逐项提问确认；信息不足时不自行脑补需求；更新报告时只保留最新需求，不迁移过时内容。

### `dev-doc-writer` —— 开发文档

- **职责**：把已确认的 Issue 转成可落地的开发文档与配套流程图。
- **输入**：Issue 内容、代码库上下文。
- **产出**：`docs/dev-docs/` 下的目录结构文档（`目录结构.md`）、开发文档（数据结构、函数定义，含公开属性与多线程属性）、配套流程图（状态流转、函数内运行流程）。
- **关键行为**：先建立 / 确认目录结构文档，再与人类确认读写与只读工作区；默认私有公开属性；需求不涉及多线程时默认普通函数；设计终稿交由人类决定，人类设计能满足需求时优先采用。

### `task-planner` —— 任务拆分

- **职责**：把开发文档拆成可执行、可排序、可验收、可追踪的原子任务文件与执行顺序文件。
- **输入**：开发文档。
- **产出**：`docs/dev-docs/<序号>/` 下的任务文件 `<编号>-<任务>.md`（含编号、任务、工作区、依赖、产出、验收标准，及从开发文档摘录的函数/结构体/数据库表）与执行顺序文件 `执行顺序.md`。
- **关键行为**：依赖关系必须由拆分阶段显式产出、禁止循环依赖；执行顺序由 `scripts/topo_sort.py` 扫描任务文件后拓扑排序生成，不手工排序；任务粒度以「能独立验证」为准，每个任务须声明其工作区。

### `implementer` —— 编码实现

- **职责**：按任务清单逐项实现代码改动。
- **输入**：任务清单、代码库。
- **产出**：代码改动，并逐项标记任务完成。
- **关键行为**：严格按清单推进，不做清单之外的重构或「顺手改进」。

### `tester` —— 测试验证

- **职责**：按验收标准验证实现结果。
- **输入**：代码改动、验收标准。
- **产出**：测试用例 + 测试结果报告（通过 / 失败项、回归范围、未覆盖项说明）。
- **关键行为**：以验收标准为准绳；失败即如实报告，并给出定位信息。

### `pr-creator` —— 提交 PR

- **职责**：把验证通过的改动整理为一份信息完整的 PR。
- **输入**：代码改动、Issue、开发文档、测试报告。
- **产出**：PR 标题与描述（背景、改动摘要、验证方式、影响面、回滚方案）。
- **关键行为**：PR 描述自包含——评审者无需回溯上下文即可理解改动理由。

## 快速开始

1. 确认所使用的 AI 编程工具支持 Skill，即能够加载 `SKILL.md` 形式的指令文件。
2. 将 `skills/` 下所需的 Skill 目录放入该工具的 Skill 目录：
   - **Codex**：Skill 目录路径 `TBD`
   - **TRAE**：Skill 目录路径 `TBD`
   - 若工具不支持全局 Skill 目录，也可把 `SKILL.md` 放在项目内，并通过工具的规则文件（如 `AGENTS.md`）引用。
3. 在对话中依次触发各 Skill：先由 `issue-writer` 收敛需求，再按流程推进；也可以只调用其中某一个 Skill。
